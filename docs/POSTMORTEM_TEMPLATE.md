# 事故复盘模板（Postmortem Template）

> 本文件是**空模板**，供 [`OPERATIONS.md`](OPERATIONS.md) §9 事故响应流程的 **§9.3「如何记录」**使用：
> 复制成一份复盘记录后逐节填写。**它不是事故台账**——本文件只定义格式与字段，本身不含任何真实事件。
> **首份已填写的实例**见 [`archive/incident-20260916-presign-empty-url.md`](archive/incident-20260916-presign-empty-url.md)
> （2026-09-16 代码险情 near-miss，2026-09-30 按归档四步冻结）——本仓库**尚无真实线上事故**的复盘记录，
> 填写下一份前先读它的「取证纪律」：没有运行期实测值的字段写「未留存 + 原因」，**不编造数据**。
>
> 证据等级沿用 [`OPERATIONS.md`](OPERATIONS.md) §1.1 的三档（**代码强制** / **文档约定** / **建议值**）。
> 凡标注「（**建议**）」的字段都是本模板的推荐做法，**未在代码或 CI 中强制**——不要把它当成已生效的流程。

## 0. 适用范围与填写须知

| 事项 | 约定 |
|---|---|
| 适用 | [`OPERATIONS.md`](OPERATIONS.md) §9.1 的 **P0–P3** 事件；未造成损失但险些发生的险情（near-miss）**建议**同样记录 |
| 适用（**灾难恢复演练**） | [`OPERATIONS.md`](OPERATIONS.md) §7.3 的定期 DR 演练**建议**复用本模板——**不新增文件**。**演练不是事故**：事件等级填「演练」，不套 P0–P3 定级，并把摘要 / 影响面 / 时间线 / 根因按演练语境改写（「影响面」= 若这是真实事故会损失什么），另补填下方「演练复盘补充字段」 |
| 不适用 | **安全漏洞的报告**走 [`../.github/SECURITY.md`](../.github/SECURITY.md) 私有渠道，先公开复盘会泄题；纯咨询 / 观测疑问（§9.1 的 P3 记录类）**建议**只填 §1–§4 |
| 记录人 | 事故的**响应者**本人（**建议**），不是事后旁观者 |
| 复盘对象 | **系统与流程**（代码 / 配置 / 告警 / Runbook / 文档盲区）；**不用于绩效追责**（**建议**） |
| 时限 | 事件闭环后 **5 个工作日**内完成初稿（**建议**；本仓库无 SLA、无强制时限，见 [`../.github/SUPPORT.md`](../.github/SUPPORT.md)） |
| 行动项 | 每条**必须**有负责人与截止日期；无 owner 的条目不要写进 §9，改登记 [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md) 待认领 |
| 存档 | 填写完成后按 [`archive/index.md`](archive/index.md)「归档操作」`git mv` 冻结进 `docs/archive/`，命名 `incident-YYYYMMDD-<短名>.md`，并在该索引登记一行 |

## 1. 元信息

| 字段 | 填写 |
|---|---|
| 复盘编号 | `PM-YYYYMMDD-<短名>`（**建议**格式，全仓唯一） |
| 事件等级 | P0 / P1 / P2 / P3（判据见 [`OPERATIONS.md`](OPERATIONS.md) §9.1） |
| 发生 / 发现 / 恢复时间 | 本地时间含时区，格式 `YYYY-MM-DD HH:MM +08:00` |
| 影响时长 | 发现 → 恢复的总时长；其中「人工止损耗时」另计（见 §7） |
| 发现方式 | 告警 / 用户报障 / 例行巡检 / 巧合（决定 §6 要补哪一环） |
| 记录人 / 复核人 | 账号或标识 |
| 关联条目 | `KNOWN_ISSUES #N` / `ROADMAP §三 #N` / issue / commit 短 SHA |

## 2. 摘要（≤3 行）

> 一句话说清：**什么坏了 → 影响谁 → 为什么 → 怎么修好的**。不写过程，过程放 §4。

## 3. 影响面

| 维度 | 填写 |
|---|---|
| 账号 / 桶 / 对象 | 受影响的具体范围与数量 |
| 数据完整性 | 是否丢失 / 覆盖 / 明文落盘；是否有**半成品**（`GET /api/migrate/jobs` 里的 `interrupted` 项） |
| 对外可用性 | `/api/health` 状态、5xx 比例、持续时长（对齐 [`OPERATIONS.md`](OPERATIONS.md) §4 的 SLI） |
| 安全影响 | 是否疑似未授权访问 / `S3C_TOKEN` 或 `S3C_STORE_KEY` 泄露；若是，**先按 §9.1 止损、按 §9.2 决策**，再走 SECURITY.md 私有渠道 |

## 4. 时间线

| 时间 | 类型（发现 / 动作 / 观测 / 决策） | 内容 | 证据（请求 ID / 命令 / 截图路径） |
|---|---|---|---|
|  |  |  |  |

## 5. 取证清单（对照 §9.3 第 1 步）

> 勾选「已留存」；**未留存的写原因**——取证时没存，事后补不回来。

| 证据 | 已留存 | 位置 / 命令 |
|---|---|---|
| `/api/health` 响应体 | ☐ | `curl -sS http://127.0.0.1:5000/api/health` |
| `/api/metrics` 全文 | ☐ | 需 `S3C_EXPOSE_METRICS=1`；未开启就注明「端点默认 404」 |
| 最近 15 分钟 server 日志 | ☐ | `docker compose logs --since 15m server` |
| nginx 访问日志 | ☐ | `docker compose logs nginx \| grep 'req=<id>'`（字段 `rid=` / `req=` 的区别见 §3.3） |
| 数据目录状态 | ☐ | `ls -l "$S3C_DATA_DIR"`（目录 0700 / 文件 0600） |
| `jobs.json` 副本 | ☐ | 先复制再排查，**不要**原地改动 |
| 审计事件检索结果 | ☐ | 检索 `msg="audit"`，事件名清单见 §3.3 |

## 6. 根因分析

- **触发因素**（导火索）：…
- **根因**（缺了哪道防线才会发生）：用「5 Why」追问到**可改动的一层**（代码 / 配置 / 告警 / 文档）为止。
- **为什么没被更早发现**：告警缺失 / 阈值不当 / 无探针 / 无演练（对照 §4.2 告警基线）。
- **同类风险是否仍在**：在 → 登记 [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md)（唯一问题来源），不要只写在本文里。

## 7. 检测与响应评估

## 7.1 演练复盘补充字段（**仅灾难恢复演练**填写；非演练可整节删除）

> 用途：把 [`OPERATIONS.md`](OPERATIONS.md) §7.3「每季度至少演练一次，并记录**实测** RTO / RPO 回填 §7.1」
> 这条**建议**变成可复制的记录骨架。本节**不新增文件**、也**不引入新指标**——所有对照值都取自
> [`OPERATIONS.md`](OPERATIONS.md) §7.1 的**建议 RTO / RPO**（**建议值，未强制**，不是 SLA、也**不是**
> 本仓库承诺的硬指标）。真实事故复盘**不填**本节。

| 字段 | 填写 |
|---|---|
| 演练场景 | 对应 [`OPERATIONS.md`](OPERATIONS.md) §7.1 的哪一行：进程 / 容器崩溃 · 数据卷损坏 / 误删 · 宿主机 / 节点整体丢失 · `S3C_STORE_KEY` 丢失 · 上游 S3 不可用（可多选，逐行分别填实测值） |
| 触发方式 | 怎么触发的：`docker compose down` / 手工删除数据卷 / 在干净环境重建 / 故意不给 `S3C_STORE_KEY`（§7.3 第 3 步）等；写明**是否在真实数据上做**（**建议**只在副本 / 演练环境上做） |
| 实测 RTO | 发现 → 恢复的实际耗时（含人工介入）；**对照**是 §7.1 对应行的「建议 RTO」（**建议值**）。超出时写原因（人不在 / 备份在异地 / 步骤缺失），**不要**直接把建议值当成应达标值 |
| 实测 RPO | 实际丢失的数据时间窗；**对照**是 §7.1 对应行的「建议 RPO」（**建议值**）。另记「备份间隔」与「上次备份时间点」——驱动 RPO 的是它们，不是本表 |
| 恢复验证结果 | 逐条对照 [`OPERATIONS.md`](OPERATIONS.md) §6.4 的 6 步填写（与 §8 同一口径）；任何一步为「未验证」都要点名 |
| **未覆盖路径** | 本次演练**没能**覆盖的场景 / 步骤（如只演练了本地卷、未演练异地备份取回；只演练 `encrypted`，未演练 `sqlite`；桌面端无自动更新通道）。每条**必须**给出下一步：补进下次演练计划，或登记 [`KNOWN_ISSUES.md`](KNOWN_ISSUES.md)（唯一问题来源） |
| 密钥可用性 | `S3C_STORE_KEY` / `S3C_TOKEN` 是否**真的**从独立保管处取回并可用（[`OPERATIONS.md`](OPERATIONS.md) §6 第 4 条：只验证备份文件存在**不算**验证） |
| 下次演练 | 计划日期与目标场景（覆盖本次的「未覆盖路径」） |

## 8. 处置与验证

1. **实际执行的动作**：与 §4 时间线一一对应；被否决的方案也要写，并说明否决原因。
2. **恢复验证**：**逐条**对照 [`OPERATIONS.md`](OPERATIONS.md) §6.4 的 6 步填写实测值
   （健康与版本 / 账号清单 / 逐账号真实连通性 / `s3c_build_info` 版本一致 / `interrupted` 对账 / 15 分钟观察）。
3. **若涉及回滚**：是否按 [`DEPLOYMENT.md`](DEPLOYMENT.md) §7 执行、回滚前后的存储格式（`S3C2` / `S3C3`）与备份取用记录。

## 11. 本模板刻意不定义的事（避免发明仓库里没有的规则）

- **值班轮换与升级链**：仓库不定义，由部署方自定（[`OPERATIONS.md`](OPERATIONS.md) §9.2）。
- **强制时限与 SLA**：本仓库无 SLA、无商业支持；上文「5 个工作日」只是**建议**。
- **是否对外公开**：由部署方决定；涉及安全的一律先走私密渠道。
- **事故统计看板 / 复盘数量指标**：当前不存在，也不预先承诺数字——沿用 [`compatibility.md`](compatibility.md) §7 的同一口径（原文：「没有固定的时间窗或版本数承诺」）。
