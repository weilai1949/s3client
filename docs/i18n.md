# 国际化与本地化（i18n）

> 本文件说明 s3clinet 前端的文案体系：**当前支持哪些语言、字典放在哪、怎么加一条文案、
> 怎么加一门语言**，以及覆盖率门禁如何强制「两种语言逐键对齐」。
> 真值来源是 `apps/web/src/i18n/` 下的实际代码与测试；本文件只做导航与操作说明，
> 与代码不一致时**以代码为准**，并请顺手修正本文件。
> 相关：[`glossary.md`](glossary.md)（术语）· [`accessibility.md`](accessibility.md)（可访问性）· [`FEATURES.md`](FEATURES.md) §一.12

## 1. 现状

| 项 | 值 | 依据 |
|---|---|---|
| 支持语言 | `zh-CN`、`en-US`（联合类型 `Locale`，**二选一**） | `apps/web/src/i18n/messages/types.ts` |
| 默认语言（回退值） | `zh-CN` | `index.ts` 的 `readLocale()` 末尾 `return 'zh-CN'` |
| 持久化键 | `localStorage['s3c.locale']` | `index.ts` 的 `const LS_LOCALE = 's3c.locale'` |
| 语言切换入口 | 顶栏第二个圆形按钮，点击调用 `cycleLocale()`，在 `zh-CN → en-US → zh-CN` 之间循环 | `App.vue`（`onCycleLocale` / `localeLabel` / `<button class="theme-btn" …>`） |
| 切换按钮文案 | `locale.zh`（中文）/ `locale.en`（EN），**两种语言下都显示同一对字面量** | `i18n/messages/common.ts` |
| 翻译 API | `t(key)` 取单条；`tf(key, vars)` 做 `{name}` 占位替换 | `index.ts` 的 `t` / `tf` |
| 读取当前语言 | `locale()`；响应式状态另行导出 `i18nState`（`readonly`） | `index.ts` |
| 字典规模 | 6 个命名空间模块共 **682** 个 key（zh 与 en 各一份） | 见 §2 表格（按模块块内 `'键':` 行统计） |
| 覆盖率门禁 | 四指标 100%；`src/i18n/messages/**`（纯数据）被排除统计，`src/i18n/index.ts`（读 / 写 / 回退 / 循环逻辑）**纳入统计** | `apps/web/vite.config.ts` 的 `coverage.exclude` 与 `thresholds` |

### 回退逻辑（读 `index.ts`）

`t()` 是三级回退，**任一环都不抛错**：

```ts
return messages[state.locale][key] ?? messages['zh-CN'][key] ?? key
```

1. 当前语言字典里有该 key → 用它；
2. 否则回落到 `zh-CN` 字典；
3. 都没有 → **原样返回 key 本身**（用户在界面上会看到 `some.missing.key` 这种原始键）。

正因为第 3 条是「静默降级」，才会有 §4 的覆盖率门禁把它变成红灯。
`index.test.ts` 用一个专门的用例钉住这条兜底分支（`t() 对未知 key 回退为 key 本身`）。

`readLocale()` 同样只接受两个合法值，其余一律回退 `zh-CN`：非法值（如 `fr-FR`）
与 `localStorage` 抛错（隐私模式 / 被禁用）两个分支都有行为断言
（`index.test.ts` 的 `readLocale：…` 三个用例）。

## 2. 消息模块结构

字典按**功能域（命名空间）**拆成 6 个模块 + 1 个类型文件，放在
`apps/web/src/i18n/messages/`：

| 文件 | 命名空间示例 | 覆盖范围（文件头注释原文） | key 数 |
|---|---|---|---:|
| `common.ts` | `nav.*` / `common.*` / `theme.*` / `locale.*` | 应用骨架 / 导航 / 连接状态 / 主题 / 通用按钮等高频文案 | 47 |
| `objects.ts` | `toolbar.*` / `objects.*` / `ctx.*` / `trash.*` | 对象浏览：工具栏 / 列表 / 回收站 / 右键菜单 | 133 |
| `objectDialogs.ts` | `preview.*` / `compare.*` / `tags.*` / `detail.*` / `headers.*` / `storage.*` / `acl.*` | 对象级对话框：复制/移动目标、详情、标签、HTTP 头、存储类型、ACL、预览、版本比较 | 159 |
| `buckets.ts` | `buckets.*` / `overview.*` / `website.*` / `lifecycle.*` / `encryption.*` / `policy.*` / `cors.*` / `bucketTags.*` | 桶管理与桶设置：概览 / 网站 / 生命周期 / 加密 / 策略 / CORS / 桶标签 | 149 |
| `upload.ts` | `upload.*` / `migrate.*` | 文件上传与迁移面板 | 68 |
| `accounts.ts` | `accounts.*` / `server.*` / `provider.*` / `region.*` | 账号管理 / 服务器设置 / 服务商预设 | 126 |
| `types.ts` | — | 只放共享类型：`Locale` 与 `MessageBundle`，**不含任何文案** | — |

> key 数按各文件 `'zh-CN': { … }` 块内的 `    '键':` 行统计（口径见本文件末「统计口径」）；
> 682 = 全部 6 个模块之和，且模块之间**没有重复 key**（见 §5）。

每个模块的形状完全一致——导出一个 `MessageBundle`，两种语言各一个大对象：

```ts
import type { MessageBundle } from './types'

/** 账号管理 / 服务器设置 / 服务商预设。 */
export const accountsMessages: MessageBundle = {
  'zh-CN': {
    'accounts.title': '账号管理',
    // …
  },
  'en-US': {
    'accounts.title': 'Accounts',
    // …
  },
}
```

`index.ts` 负责把它们**合并成运行时字典**（`mergeBundles`），并在此处决定合并顺序：

```ts
const messages = mergeBundles(
  commonMessages, objectsMessages, objectDialogsMessages,
  bucketsMessages, uploadMessages, accountsMessages,
)
```

`MessageBundle` 的类型定义强制每个模块**必须同时提供两种语言**：

```ts
export interface MessageBundle {
  'zh-CN': Record<string, string>
  'en-US': Record<string, string>
}
```

### 为什么要拆分

- **可维护性**：单文件字典会随功能增长到数千行，任何一次改动都要在大文件里定位；按域拆分后，
  改桶设置只碰 `buckets.ts`。
- **门禁定位精度**：`coverage.test.ts` 报错时会带出**文件路径**
  （如 `某键 @ messages/objects.ts`），拆分让「该去哪修」一目了然。
- **覆盖率口径可以更细**：模块化之后才能把**纯数据**（`messages/**`）排除出覆盖率统计，
  同时把 `index.ts` 的**逻辑**（读 / 写 / 回退 / 循环）留在统计内强制测到
  （见 `vite.config.ts` 的注释「i18n 曾整体排除…覆盖率去水分」）。

## 3. 如何新增一门语言（以 `ja-JP` 为例）

> 现状是**两语言硬编码**：类型是二选一联合、回退写死 `zh-CN`、循环顺序写死数组。
> 因此「加一门语言」不是加一个文件，而是**按下面 8 步改 7 个位置**，任何一步漏掉都会
> 出现「切不过去 / 显示原始 key / 门禁报错」。

| 步 | 改哪个文件 | 具体动作 |
|---|---|---|
| 1 | `apps/web/src/i18n/messages/types.ts` | 把 `Locale` 联合类型扩成 `'zh-CN' \| 'en-US' \| 'ja-JP'` |
| 2 | 6 个消息模块 `messages/{common,objects,objectDialogs,buckets,upload,accounts}.ts` | 每个 `MessageBundle` 里**新增第三种语言块** `'ja-JP': { … }`，key 与现有两种语言**逐键一致** |
| 3 | `apps/web/src/i18n/index.ts` → `mergeBundles` | 返回值里加一行 `'ja-JP': Object.assign({}, ...bundles.map((b) => b['ja-JP']))`（类型改了之后这里会先编译报错，改完即恢复） |
| 4 | `apps/web/src/i18n/index.ts` → `readLocale` | 校验分支加 `\|\| v === 'ja-JP'`（否则持久化的 `ja-JP` 会被当非法值丢掉、静默回退 `zh-CN`） |
| 5 | `apps/web/src/i18n/index.ts` → `cycleLocale` | 循环数组加进 `order`：`['zh-CN', 'en-US', 'ja-JP']`（顺序改动的影响见 `index.test.ts` 的「`cycleLocale` 在 zh-CN → en-US → zh-CN 之间循环」，该用例需同步改写） |
| 6 | `apps/web/src/App.vue` | 语言按钮标签目前是二元判断（`i18nState.locale === 'zh-CN' ? t('locale.zh') : t('locale.en')`），需改成按 `Locale` 映射；`i18n/messages/common.ts` 补 `locale.ja` 之类的标签 key（**zh / en 两份都要补**） |
| 7 | `apps/web/src/i18n/coverage.test.ts` | `keysOfLocale(loc: 'zh-CN' \| 'en-US')` 的入参类型、以及「中英字典的键集合逐键一致」用例需扩成**三种语言两两比对**；否则新语言缺 key 不会被发现 |
| 8 | `apps/web/src/i18n/index.test.ts` | 现有用例大量 `setLocale('en-US') … setLocale('zh-CN')`；新增语言后补一条「切到 `ja-JP` 再切回」的循环断言，保持 `cycleLocale` 分支覆盖率 100% |

补充说明：

- **`messages/*.ts` 的键完整性由门禁兜底**：第 2 步漏了某个 key，`coverage.test.ts` 的
  「中英字典的键集合逐键一致」用例会红（但**前提是第 7 步已把新语言纳入比对**）。
- **`index.html` 的 `<html lang="zh-CN">` 是静态值**，切换语言时**不会**被更新——
  加语言时若需要正确的文档语言标记，得另行改动，本仓库当前没有这处逻辑。
- **区域名是刻意的例外**：`apps/web/src/regions.ts` 的 `regionLabel()` 只在 `zh-CN` 下用预设中文标签，
  其它语言一律显示 region code（约 140 个区域不为每种语言各建一套 key，注释写明「避免为 ~140 个区域各建 i18n key」）。
  新语言沿用这一策略即可，**不要**去补区域表。

## 4. 如何新增一条文案

1. **先选模块**：按 `apps/web/src/i18n/messages/` 里各文件的文件头注释判断归属
   （高频骨架 → `common.ts`；对象列表 / 右键菜单 → `objects.ts`；对象对话框 → `objectDialogs.ts`；
   桶与桶设置 → `buckets.ts`；上传 / 迁移 → `upload.ts`；账号 / 服务器 → `accounts.ts`）。
2. **在 `zh-CN` 块里加 key**，命名用「命名空间.小驼峰」，与同命名空间既有键保持风格一致。
3. **在同一个文件的 `en-US` 块里加同名 key**——这是硬要求，不是建议：
   - 只加 `zh-CN`：`coverage.test.ts` 的集合级双向比对会红（`missingInEn` 非空）；
   - **留空串**（`'k': ''`）也会红：「每个键的两种语言取值都非空」用例专治占位空串。
4. **需要插值时用 `tf()`**，占位符写成 `{name}`，并在两种语言里都保留同名占位符
   （如 `objects.noMatch`、`dest.selected`）。
5. **在代码里引用**：组件 / 组合式函数里 `import { t, tf } from '../i18n'`，直接 `t('your.key')`。
   注意 `t` / `tf` 的字面量键会被静态扫描（见下），**动态拼接键有额外要求**。
6. **跑门禁**：

   ```bash
   cd apps/web && pnpm test src/i18n/coverage.test.ts
   ```

### 覆盖率门禁到底强制了什么

`apps/web/src/i18n/coverage.test.ts` 不经过任何 mock，用 Vite 的
`import.meta.glob('?raw')` **直接读源码文本**与**字典文本**做静态比对（因此前端不需要
`node:fs` / `@types/node`，见 [`decisions/0004-minimal-frontend-deps.md`](decisions/0004-minimal-frontend-deps.md)）。
它一共 6 个用例，每个对应一类真实事故：

| 用例 | 挡住的事故 |
|---|---|
| 扫描到源码与字典（前置自检） | 路径 / 解析失效导致的**空跑变绿**（源码 > 50 个、字典 > 3 个） |
| 每个被引用的字面量键都有定义 | **用户看到原始 key**：`objects.toastCopyFailed` / `batchEdit.tagsNeedKey` / `common.working` 三个键曾被引用却未定义，而当时的测试用 `vi.mock` 回显 key，断言 `toBe('...key')` 恒真，改不出来（2026-09-16 评估 L4 / R1） |
| 字典中不存在未被引用的死键 | **字典膨胀**：反向门禁，之前只查「引用 → 定义」，导致约 40 个死键堆积、键数虚高（评估 D7） |
| 字典非空（键数 ≥ 640） | 规模下限，防字典被整体清空 / 扫描口径失效后仍然「全绿」 |
| 中英字典的键集合**逐键**一致 | **只比数量**的漏洞：zh 缺 `a`、en 多一个 `b` 时数量相等，门禁仍绿，用户切到英文就看到原始 key |
| 每个键的两种语言取值都非空 | 占位空串（翻译「先占个位」） |

两个实现细节值得知道：

- **注释里的键名不算「已使用」**：扫描前先按字符扫描剥离注释（并正确跳过字符串字面量，
  避免把 `'https://x'` 的 `//` 当注释）。否则「删掉真实引用、只在注释里留个键名」也能骗过死键门禁。
- **动态拼接键按形状豁免**：形如 `` `provider.${p}.label` `` 的模板字面量在源码里不存在完整字面量，
  死亡判定会误报，因此按「字面命名空间前缀 + 插值」生成豁免正则（当前全仓 4 处：`provider.group` /
  `provider.label` / `provider.desc` / `storage.class`）。豁免形状**必须收紧**——初版没有收紧，
  `/api/accounts/${id}`、`Bearer ${token}` 这类非 i18n 模板串生成了几乎匹配任意键的正则，
  门禁由「26 个死键」退化成「0 个死键」（恒真）。

## 5. 常见错误

| 现象 | 原因 | 处理 |
|---|---|---|
| 界面上出现 `xxx.yyy.zzz` 这种原始键 | 该 key 在**当前语言**字典里没定义，`t()` 走完了三级回退（当前语言 → `zh-CN` → key 本身） | 用 §4 的步骤补 key；`coverage.test.ts` 的两个用例（引用→定义、集合逐键一致）会在 CI 先红 |
| 只加了一门语言的 key | 集合级双向比对报出 `missingInEn` / `missingInZh` 列表 | 补齐另一门；**不要**用空串占位，空串另有用例拦截 |
| 新加的 key 让「死键」用例变红 | key 已定义但生产代码里**没有任何引用**（测试文件里的引用不算） | 要么补上真实引用，要么删掉该 key——本仓库不接受「先囤着，以后用」的字典项 |
| 动态拼接的 key 被误判为死键 | 它是模板字面量，源码里不存在完整字面量 | 保持「字面命名空间前缀 + 插值」形状（如 `` `storage.class.${sc}` ``）；不要写前缀本身也是变量的形状（如 `` `${ns}.title` ``），那种形状无法生成安全豁免，会被判死键 |
| **两个模块定义了同一个 key，谁生效？** | `mergeBundles` 用 `Object.assign` 顺序覆盖，**合并顺序里靠后的模块赢**：`common → objects → objectDialogs → buckets → upload → accounts`，即同名 key 最终取 `accountsMessages` 的值（同语言内） | 当前 6 个模块之间**没有重复 key**（682 = 各模块 key 数之和），但这不靠门禁保证——`coverage.test.ts` 只校验「键集合逐键一致」与「死键」，**不校验跨模块唯一性**。因此新增 key 前先在全目录搜一次同名键；一旦重复，先改名的那个模块会让另一个模块的文案静默失效（中文 / 英文各自覆盖） |
| `pnpm test` 里 i18n 相关用例红，但界面看起来正常 | 覆盖率门禁要求 `src/i18n/index.ts` 的**每条分支**都有行为断言（`readLocale` 的异常 / 非法值 / 合法值、`setLocale` 写入失败、`cycleLocale`、`locale()`），改了这些分支就要同步改 `index.test.ts` | 按 `index.test.ts` 现有用例风格补行为断言（断言外部可见结果，不要断言内部变量） |

## 6. 手工验证清单（改完文案 / 加语言后）

```bash
cd apps/web
pnpm test src/i18n            # 字典门禁 + 语言状态机用例
pnpm test                     # 全套单测（覆盖率达到 100% 才能过）
pnpm build                    # vue-tsc 类型检查 + 构建
```

界面上依次核对：

1. **默认中文**：清掉 `localStorage['s3c.locale']` 后刷新，界面为中文。
2. **切到英文**：点顶栏语言按钮，导航、工具栏、对话框标题与按钮、toast、空态文案全部变英文，
   **不出现**任何 `.` 分隔的原始键。
3. **刷新后保持**：刷新页面仍是英文（`s3c.locale` 持久化生效）。
4. **切回中文**：再点一次回到中文。
5. **重新打开**：新增 / 修改过的弹窗、右键菜单、确认框逐处打开看一眼（这些是文案最密集的地方）。

## 统计口径

本文件的 key 数（47 / 133 / 159 / 149 / 68 / 126，合计 682）由以下命令在
`apps/web/src/i18n/messages/` 目录下统计：先取各文件 `'zh-CN': {` 到对应收尾 `},` 的块，
再数块内以 `    '` 开头且首字符为字母的键行；`types.ts` 不计（无文案）。
模块间无重复 key，因此 682 同时等于各模块 key 数之和与运行时字典的键数。
若后续字典增长，请同步更新 §1 与 §2 的数字（`coverage.test.ts` 的规模下限是 640，不会替本文件校对）。
